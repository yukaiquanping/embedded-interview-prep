# Linux 与网络基础：16 题

[返回目录](../README.md) · 用“执行上下文、所有权、失败路径、验证方式”串联回答。

## L01. 进程与线程的主要区别是什么？

**参考回答：**进程通常具有独立虚拟地址空间；同进程的线程共享地址空间、文件描述符表等资源，各自有执行上下文和栈。共享更方便，也使数据竞争和错误传播更直接。线程创建和切换成本需具体测量，不能绝对说线程总比进程快。

**追问：**同进程两线程并发关闭或重用一个文件描述符有什么风险？需要明确所有权与生命周期，避免编号被重用后误操作其他连接。

## L02. 为什么条件变量等待通常放在 `while` 中？

**参考回答：**唤醒只是通知重新检查共享条件，不保证当前线程恢复运行时条件仍成立；也可能发生虚假唤醒。等待前持锁检查谓词，等待过程原子地释放锁并进入等待，返回时重新持锁，再检查条件；还应处理超时及退出状态。

**误区：**条件变量不是自动累计业务事件的消息队列。仅发送信号而不保存条件状态，容易产生丢失通知问题。

## L03. 互斥锁、自旋锁应该怎样区分？

**参考回答：**先区分用户态与内核，再讨论上下文。普通内核自旋锁适合不能睡眠的短临界区，持锁期间不能调用可能睡眠的操作；内核 mutex 适合可睡眠上下文。还要分析中断、抢占、多核及锁顺序。实时内核可能改变部分锁的实现，不能脱离内核配置背口诀。

**追问：**驱动用 `spin_lock` 保护后调用用户内存拷贝是否合适？用户页访问可能缺页，不能把可能睡眠的操作塞入该临界区。依据：[Linux 5.4 Driver Basics](https://www.kernel.org/doc/html/v5.4/driver-api/basics.html)。

## L04. `read()` / `write()` 返回短长度意味着什么？

**参考回答：**一次调用可能只完成部分数据，调用者需要按接口语义推进偏移并处理后续调用。错误时区分 `EINTR`、`EAGAIN` 和真正失败；非阻塞 IO 不能忙等。请求接收长度大于零时，流式 socket 的 `recv` 返回零通常表示对端有序关闭发送方向，并不表示“暂时没数据”。

**追问：**写循环如何避免永不退出？处理无进展、总超时、取消和连接关闭，不仅检查负返回值。

## L05. 阻塞、非阻塞与 IO 多路复用有什么关系？

**参考回答：**阻塞描述调用是否等待条件满足；非阻塞在当前无法完成时及时返回。`select`、`poll`、`epoll` 用于等待多个描述符的就绪事件，不自动完成业务 IO。就绪之后仍要处理短读写与状态变化。

**追问：**边缘触发为什么常配合非阻塞并读到 `EAGAIN`？否则缓冲里剩余数据可能没有新的状态变化来再次通知。并要考虑单连接处理配额，防止饿死其他连接。

## L06. 应用访问设备的一般路径是什么？

**参考回答：**应用通过系统调用、设备节点或其他内核接口进入子系统；内核根据打开对象与操作表调用驱动，再由驱动访问控制器和硬件。`/dev` 节点存在只能说明某个接口已建立，不能证明传感器、采集链或引脚配置正常。

**项目联系：**V4L2 与 ALSA 应用通常通过各自子系统工作，不需要每个应用直接操作硬件寄存器。

## L07. 交叉编译成功为什么仍可能运行失败？

**参考回答：**编译器架构、ABI、浮点约定、动态加载器和目标运行库必须匹配。内核模块还需匹配目标内核配置、符号和构建环境。用 `file`、`readelf`、目标设备日志定位，避免直接在宿主机执行不明目标二进制。

**追问：**文件存在却提示无法执行或找不到文件？除权限和架构外，检查 ELF 指定的动态加载器路径是否存在。

## L08. 内存泄漏、越界和释放后使用怎样区分？

**参考回答：**泄漏是仍分配但不再可达或不再释放；越界是访问对象合法范围外的内存；释放后使用是生命周期结束后继续访问。分别检查分配释放配对、长度与索引、异步回调的所有权。用编译警告、宿主机 sanitizer 和目标平台工具配合复现，不能因一次没崩溃就认为安全。

**追问：**异步任务退出时如何防止回调访问已释放上下文？先停止接收新任务、撤销回调或等待在途回调完成，再释放资源。

## N01. TCP 和 UDP 应该怎样选择？

**参考回答：**TCP 提供可靠、有序的字节流，应用仍需定义消息边界；UDP 保留数据报边界，但不承诺到达、顺序或去重。控制和媒体可选择不同传输方式，依据延迟、容错和实现成本决定，不能说“UDP 天生低延迟，所以一定好”。

**依据：**[TCP 规范 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。项目中 UDP 呼叫控制需要应用层超时、确认和幂等设计。

## N02. 所谓 TCP 粘包、半包要怎样处理？

**参考回答：**TCP 是连续字节流，一次发送不对应一次接收。可采用长度前缀或带转义的分隔符。接收端累积数据，验证头和长度上限，有完整帧才分派；处理多帧和不完整尾部，连接关闭时丢弃或报告不完整帧。

**追问：**恶意长度字段为什么危险？可能造成巨额分配、整数溢出或永远等不到数据，应设置最大帧长和接收超时。

## N03. UDP 控制消息如何做到重复到达也安全？

**参考回答：**设计会话标识、请求序号、明确状态转换和有界重试；收到重复请求时复用结果或重新确认。用会话代际丢弃旧包，所有终止路径统一回收资源。来源地址过滤不等于身份认证，鉴权与重放防护要另行设计。

**误区：**重传不保证必达；若没有最大重试和总超时，会把故障变成永久等待。

## N04. 心跳为什么不能证明媒体正常？

**参考回答：**心跳证明的是特定时间内控制链路或任务有响应。音频采集、编码、端口、播放设备可能单独出错。应分别观察控制状态、媒体包计数、管线错误、播放进度及缓冲占用，定义不同健康信号。

**追问：**心跳超时依据什么时钟？使用单调时钟衡量间隔，避免系统时间被校正后误判。

## N05. WebSocket 返回 101 就说明语音服务已经正常吗？

**参考回答：**101 仅表示符合相应握手条件后协议升级成功，不能证明业务鉴权、会话初始化、音频事件和云端推理都成功。按“DNS/TCP/TLS → HTTP 升级 → 业务 session → 上行事件 → 下行 → 播放”逐层定位。

**依据：**[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)。应用消息和状态由具体服务协议定义。

## N06. RTP 序号和时间戳分别干什么？

**参考回答：**序号帮助识别丢失、重复与乱序；时间戳表示媒体采样时序，单位由负载时钟决定，不一定是毫秒。它们不提供自动可靠重传。不同音视频时钟的同步需要额外映射与播放策略。

**依据：**[RFC 3550](https://www.rfc-editor.org/rfc/rfc3550.html)。不能因为项目用了 RTP 就宣称已经完成 RTCP 音画同步。

## N07. GUI 为什么不能在网络回调中随意更新？

**参考回答：**先确认回调实际在哪个线程。Qt GUI 应在主线程操作，工作线程通过排队信号等方式交付结果；对象还要满足线程亲和性和生命周期要求。其他嵌入式 UI 框架应按其任务模型，通过消息或待刷新标志交接。

**依据：**[Qt 5 Threads and QObjects](https://doc.qt.io/archives/qt-5.15/threads-qobject.html)。把耗时网络调用放进 GUI 线程会影响输入与重绘。

## N08. 遇到“没声音 / 没画面”怎样开始排查？

**参考回答：**先确定方向、设备、时间和是否可稳定复现，再把链路拆为采集、格式转换、编解码、发送、接收、解码和输出。用本地录放/预览隔离硬件，用计数与日志定位边界，再做最小单变量实验并复测。

**项目练习：**语音输入有数据、队列增长却无发送回调，应先调查事件循环和可写唤醒；收到媒体包却无声，应继续检查格式、解码和输出路由。
